# ADR 0004 — Auth

**Decision:** Cognito Essentials
**Options rejected:** Self-rolled (security risk on health data — stated plainly); Auth0/Clerk (paid tiers)
**£/mo:** £0
**Reversal cost:** High — user migration is painful

## Amendment, Gate G1 (2026-08-21) — two user pools, not one

Added ahead of Phase 2, the same way ADR-0017 was added at G0 ahead of Phase 1: elaborating TASK 2.2.1 surfaced a constraint the one-line decision above does not survive.

**The constraint.** D-09 wants **TOTP for clinicians and email-OTP for patients**. Cognito's MFA policy is *pool-wide*: `REQUIRED` would stack a second factor on top of a patient's passwordless email OTP, and `OPTIONAL` cannot compel a clinician to enrol. One pool cannot hold both policies.

**Decision:** two user pools in `eu-west-2` — `ndn-patients` (self sign-up on, passwordless email OTP, no MFA) and `ndn-clinicians` (self sign-up disabled at the directory level, password plus `REQUIRED` TOTP). Beyond resolving the MFA policy, this makes the patient/clinician boundary structural: a patient credential cannot become a clinician credential, because the two are not in the same directory. Group membership within one pool is a softer boundary than that, and on a system holding clinical records the harder one is worth its cost.

**What it costs, stated rather than buried:** API Gateway's built-in JWT authorizer binds one issuer per authorizer and one authorizer per route, so two issuers mean a Lambda authorizer instead (TASK 2.2.2) — one more function on the authenticated request path, mitigated by API Gateway's 300-second authorizer result cache and the same arm64/128 MB/no-VPC shape as everything else. £0 either way; 509 MAU across both pools remains far inside the 10,000 free.

**Options rejected:** one pool with `cognito:groups` for roles — cheaper, lower latency, and the built-in JWT authorizer would serve. Rejected on the MFA conflict above, whose only workaround is a Pre-Authentication trigger reimplementing enforcement that Cognito already does correctly one pool boundary away.

**Not enabled:** advanced threat protection (a paid tier). The honest position is that £0 buys the directory and the MFA, not the risk engine.

**Closed 2026-08-22, when TASK 2.2.1 built this:** the Essentials free-MAU allowance and price were re-verified as that task's first step, per the gate checklist's 90-day rule. **Unchanged** — 10,000 MAU free per account or per AWS organization, always-free rather than a 12-month offer, $0.015/MAU beyond it in `eu-west-2` (usage type `EUW2-CognitoEssentialsMAU` in the AWS Price List). 509 modelled MAU leaves ~19x headroom, and `ndn-prod`'s organization has no other Cognito user pools competing for the shared allowance. Working and caveats: [docs/runbooks/cognito-user-pools.md](../runbooks/cognito-user-pools.md).

## What TASK 2.2.1 found that this ADR should not have assumed

Two lines of the decision above cannot be expressed in Cognito as written, and the implementation records what was built instead rather than letting the ADR keep claiming them.

**"Passwordless email OTP, no password" is a property of the app client, not the pool.** Cognito requires `PASSWORD` in a pool's `AllowedFirstAuthFactors` — the console says "The Password option is always available" and CDK rejects `password: false`. So `ndn-patients`' policy is `["PASSWORD", "EMAIL_OTP"]`. What makes the claim true is that the only app client on that pool holds `ALLOW_USER_AUTH` and nothing password-shaped, and a patient account never has a password set. The boundary is real; it just sits one layer lower than the ADR implied.

**"PKCE required" is not a Cognito setting.** There is no switch that refuses a code exchange without a `code_verifier`. What the clients have is `GenerateSecret: false` — a public client whose exchange is unauthenticated, which is precisely the case PKCE exists for. Sending `code_challenge` is TASK 2.2.4's obligation, not something the directory enforces on its behalf.

## Amendment, D-29 (2026-08-29) — the patient half of D-09 is reversed

**D-09's patient half — "email-OTP for patients" — no longer holds.** The clinician half (TOTP) is untouched. The owner's own decision, made live while reviewing this system's real-world sign-in requirements (the clinic's actual clients are in India, where SMS OTP needs TRAI/DLT registration before a single message sends, and WhatsApp OTP carries its own Meta Business verification and template-approval track — see [D-29](../plan/01-decisions.md) and [patient-account-provisioning.md](../runbooks/patient-account-provisioning.md) for the full reasoning): **remove the automated channel entirely rather than solve its regulatory dependencies.** A patient contacts the clinic's WhatsApp Business number — a human-staffed channel, not a technical integration this codebase touches — and a human creates their account and hands them a password directly. No OTP survives anywhere in this system, for either role, through any channel (email, SMS, or WhatsApp).

**What this changes, concretely, in `ndn-patients`:** `selfSignUpEnabled: false` (matching the clinician pool now); no `signInPolicy` (Cognito's password-only default is exactly what's wanted); a `passwordPolicy` identical to the clinician pool's; `accountRecovery: AccountRecovery.NONE` — the one setting this amendment could not treat as a footnote, since `ForgotPassword` is an unauthenticated Cognito API independent of the app client's auth flows, and leaving email-based recovery on would have quietly reopened self-service password reset outside the WhatsApp-verified process the whole redesign exists to enforce; the web client's `authFlows` move from choice-based (`ALLOW_USER_AUTH`) to SRP (`ALLOW_USER_SRP_AUTH`), the identical flow the clinician client has always used. The Post-Confirmation trigger this ADR's own two-pool design added a hook for (TASK 2.2.3) is deleted outright, not merely unwired — with self sign-up off, the `ConfirmSignUp` event it reacted to can never fire.

**What is unchanged.** The two-pool structural boundary this ADR's own Gate G1 amendment established — a patient credential cannot become a clinician credential, because the two are not in the same directory — is exactly as load-bearing as before; D-29 only changes the patient pool's *own* internal policy, never the boundary between the two. The clinician pool, its TOTP requirement, and its own password-over-SRP flow are untouched by any part of this amendment. The account-approval lifecycle (a clinician moving `pending` to `approved`) is likewise untouched — this amendment changes how a `pending` record comes to exist, never what happens to one afterwards.

**Options rejected, this time around, before landing on "no automation":** SMS OTP via a third-party India-focused aggregator (still needs the same underlying TRAI/DLT registration the aggregator cannot bypass on the sender's behalf); WhatsApp OTP via AWS End User Messaging Social or the WhatsApp Business Platform directly (a genuine technical option, but carries its own Meta template-approval and verification track, solving a compliance problem this system does not need to own once a human is already answering WhatsApp anyway). Both are recorded here as real alternatives that were seriously evaluated, not straw-manned past.

**Correction, same day (2026-08-29), found on this amendment's first deploy: "no `signInPolicy`" above is not quite what happened.** `UpdateUserPool` does not clear a previously-set `Policies.SignInPolicy` when the field is simply absent from a later update — `PatientUserPool` had carried an explicit `[PASSWORD, EMAIL_OTP]` policy since TASK 2.2.1, and removing the field from the CDK template left that exact value live and unchanged, even though CloudFormation's own template (and its diff) showed the field gone. Harmless in practice — the app client's `ExplicitAuthFlows` no longer offers `ALLOW_USER_AUTH`, the only flow `EMAIL_OTP` is reachable through — but dormant and undocumented is not the same as closed. Fixed by setting an *explicit* `AllowedFirstAuthFactors: [PASSWORD]` rather than omitting the field: an explicit narrower value is a real transition CloudFormation sends and Cognito applies, unlike an omission. See `infra/src/auth-stack.ts`'s own comment on the patient pool construction for the full finding.
