# ADR 0008 — SMS

**Decision:** **AWS End User Messaging SMS**, chosen at **M2.3 (TASK 2.3.2)** from live-re-verified UK prices (2026-08-22, via the AWS End User Messaging pricing page and the AWS `SendTextMessage` API reference, both fetched live that day — see "Prices" below for the method and the exact figures). Milestone renumbered from M2.2 by the Gate G1 reordering.

**Options rejected:** Twilio — $0.056/message, ~60% more expensive per message than AWS's $0.035, and its lower rate is what changes R-01's arithmetic materially (see "Why this decision, beyond price" below). Twilio remains the documented fallback if AWS End User Messaging's UK service is ever withdrawn or its terms change unfavourably (D-11's reversal-cost note below still holds).

**£/mo:** ≤£5 hard cap on message spend (C-02, unchanged — `sms-spend-cap.ts`'s `SMS_MONTHLY_CAP_PENCE`), plus a separate $2.00/month long-code origination lease once one is provisioned (`docs/plan/03-cost-model.md`) — a fixed platform cost, not part of the per-message cap, the same way a Route 53 hosted zone fee sits outside any per-request budget.

**Reversal cost:** Low — behind the notification abstraction (`services/api/src/sms-provider.ts`'s `SmsProvider` is a one-method interface; `sms.ts` calls it exactly once). A provider swap touches `sms-provider.ts` alone plus whichever `config.ts` constants name the new origination identity.

AWS's own pricing page carries the same caveat Twilio's does — rates are "provided for guidance only, and change frequently" and vary by carrier; both figures above are the base per-message rate before any carrier-specific surcharge, on the same footing as each other.

## Total cost, at R-01's own modelled volume (~150 SMS/month, 500 patients)

This is the comparison D-10/R-01 actually turn on, not the per-message rate alone:

- **AWS End User Messaging:** $2.00 (long-code lease) + up to 150 × $0.035 = **$7.25/month** if every one of the ~150 monthly reminders sends by SMS. C-02's £5 = $6.05 cap covers **≈172 messages** at this rate — the full modelled volume, with headroom, for the first time.
- **Twilio:** ~$1.00 (long-code lease, chosen over the alphanumeric route to avoid its unpublished UK registration fee/delay) + up to 150 × $0.056 = **$9.40/month** if uncapped. But C-02's £5 cap covers only **≈108 messages** at this rate — **≈42 of the ~150 monthly reminders would degrade to email every month**, not from a fault, from the arithmetic alone.

## Why this decision, beyond price

R-01's register already names the actual risk: *"§5 asks for ~150 SMS/month; C-02's £5 buys ~108"* — a real, monthly shortfall under Twilio's rate. AWS End User Messaging's $0.035 rate raises that ceiling to ~172, which **closes the shortfall** rather than merely narrowing it. The notification abstraction (2.3.1) makes the degradation path safe either way — no reminder is silently dropped under either provider — but "safe when it degrades" is a weaker property than "does not need to degrade at the plan's own modelled volume," and the second is now achievable at a lower total cost. `docs/plan/02-risk-register.md`'s R-01 row and `docs/plan/09-self-audit.md`'s red-team item 1 are updated with the corrected figures alongside this ADR.

## What was not done as part of this decision

- **No AWS account has actually leased a UK long code, and no Twilio account exists.** `services/api/src/sms-provider.ts`'s `createAwsEndUserMessagingSmsProvider` is real, tested code (against a mocked AWS SDK client, same discipline as `ses.ts`) — nothing in it can send a real message without a real, provisioned `OriginationIdentity`, which does not exist yet.
- **UK long-code provisioning and any onboarding/vetting** is **LL-02** (`docs/plan/08-long-lead.md`): owner-owned, 2–4+ weeks. Unchanged by this ADR except in one respect — the provider is now AWS End User Messaging, not Twilio, so LL-02's action is "provision a UK long code via AWS End User Messaging SMS" rather than "register a Twilio sender ID," and it should start now, not at the end of some later task (the task's own step 6).
- **The provider-side monthly spend limit** (D-11's "app-level cap *and* provider-level cap") is an AWS-account-level configuration, set once the account and origination identity exist — an owner action for the same reason SES's production-access request is (`docs/runbooks/ses-production-access.md`, LL-01). `sms-provider.ts` additionally sets a **per-message** `MaxPrice` of $0.10 (`DEFAULT_MAX_PRICE_USD`) as a backstop independent of that account-level limit — code today, not deferred.
- **A live sandbox proof against the real provider** (the task's step 7: "drive the counter to the cap and assert the next send is refused before the provider is called") is proven today only against the mocked AWS SDK client (`sms.test.ts`, `sms-provider.test.ts`) — the equivalent proof against a real AWS account is not possible before LL-02 provisions one, and is tracked there rather than claimed here.
- **The anomalous-velocity alarm** (R-02's fifth mitigation, the task's step 8) needs a real CloudWatch metric on real send volume, which does not exist until something actually calls this code path — nothing does yet (TASK 3.4.x builds the appointment-reminder schedule). Tracked alongside that task, not fabricated against a metric that isn't emitted.
