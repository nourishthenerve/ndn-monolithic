# Clinician accounts (TASK 2.4.1)

**Date:** 2026-08-22 · **Task:** [05-execution-plan.md § TASK 2.4.1](../plan/05-execution-plan.md) · **Requirements:** §5 (clinician accounts), NFR-03 · **Decisions:** D-09 · **Risks:** [R-09](../plan/02-risk-register.md) · **Depends on:** 2.2.1, 2.2.2, 2.1.3, 2.3.1

## What this covers

`04-data-model-rbac.md`'s "Clinician accounts: C R U (deactivate only), principal alone" row becomes real: the principal clinician can invite a colleague (TOTP enrolment unavoidable, per 2.2.1's pool policy), deactivate one (record, Cognito disable and token revocation, together), and reactivate one. Nobody is ever deleted — deactivation is the only lifecycle this identity layer has, and `AdminDeleteUser` is now a repo-wide lint ban, not a habit to remember.

## Two deliberate deviations from this task's own stated text

Both forced by code that already existed when this task started, and both stated in-line where they matter (`clinician-repository.ts`'s header, `packages/shared-types/src/clinician.ts`'s header):

1. **Ordering: `AdminCreateUser` runs *before* the `CLI#` record is written, not after.** The task's own step 2 says the record is written first "so an orphaned Cognito user is the failure mode rather than an orphaned record." TASK 2.2.2's `dynamo-principal-directory.ts` already settled this differently: the `CLI#` record is keyed by the Cognito `sub` (the same decision `PAT#` records made), and there is no `sub` to key it by until `AdminCreateUser` has run. That file's own header states the resolution and that the original reason survives the reordering — an orphaned Cognito user with no `CLI#` row is exactly what `PrincipalDirectory.lookup` already treats as unauthorisable, denying it cleanly.
2. **`Clinician`'s stored shape drops the stated `subjectId` field and renames `active: boolean` to `account_status: 'active' | 'deactivated'`.** `subjectId` would just duplicate `id` (the same "the two are the same value" convention `Patient.id` already documents). `account_status` is not a naming preference: `dynamo-principal-directory.ts` reads a literal `account_status` attribute off *every* `CLI#`/`PROFILE` row, for both pools generically, to resolve a signed-in clinician's `Principal.accountStatus` — it was written before this task existed. Calling the field anything else would leave a real, active clinician unable to reach a single authenticated route.

## What was built

- **`packages/shared-types/src/clinician.ts`** — `Clinician`, `ClinicianRole`.
- **`services/api/src/clinician-repository.ts`** — `ClinicianRepository` (`create`, `findById`, `deactivate`, `reactivate`) and the `ClinicianStore` port. "Exactly one principal may exist" (step 7) is enforced by the **store**, not the handler, and atomically: `create()` throws `PRINCIPAL_ALREADY_EXISTS` when `role === 'principal'` and one already exists, race-free under concurrency (`DynamoClinicianStore`'s `TransactWriteItems`, two conditioned `Put`s in one transaction). Role transfer (step 7's other half — "a distinct, audited operation") is **not built**: nothing in this task's Tests/DoD requires it, and there is exactly one principal today with no consumer of a transfer operation — building it now would be ahead of need.
- **`services/api/src/dynamo-store.ts`** — `DynamoClinicianStore`. On a cancelled transaction, a follow-up `get()` disambiguates "id collision" from "principal slot taken" rather than parsing `TransactionCanceledException.CancellationReasons` — a real but SDK/version-shaped detail this store chose not to depend on for picking between two differently-meaning errors.
- **`services/api/src/clinician-admin.ts`** — `createClinicianAdminHandler`: `POST /clinicians` (principal-only, `can(principal, 'create', …)`), `POST /clinicians/{id}/deactivate`, `POST /clinicians/{id}/reactivate` (both `can(principal, 'update', …)` — the matrix's "(deactivate only)" qualifier is what this handler enforces by only ever calling `deactivate`/`reactivate`, never a generic field patch). **The first production route to use the real Lambda authorizer** (`request-principal.ts`'s `requirePrincipal`) rather than the admin-token bridge every other admin-shaped route stood behind at the time — this route never used the bridge, because its entire subject is clinician identity, and a real clinician principal has existed to authenticate as since 2.2.1/2.2.2 landed. [TASK 2.5.4](admin-token-retirement.md) later moved every other admin-shaped route onto the same authorizer this one always used.
- **`services/api/src/clinician-admin-handler.ts`** — wires the real Cognito Admin* calls (`AdminCreateUser`, `AdminDisableUser`, `AdminEnableUser`, `AdminUserGlobalSignOut`, `AdminGetUser`), the real `DynamoClinicianStore`/`DynamoAuditLog`, and a real `Notifier`.
- **Deactivation does all three things step 4 asks for, and none is optional:** the record transitions, `AdminDisableUser` runs, `AdminUserGlobalSignOut` runs. Record first: `can()` already re-resolves `account_status` fresh within the authorizer's 5-minute cache window regardless of what happens after, so the record change is the one that matters most; the two Cognito calls are **not** wrapped in a try/catch — a half-completed deactivation must surface loudly (500), not be swallowed as a success.
- **Invite email: Cognito's own, not the Notifier — a deliberate deviation from step 8.** `AdminCreateUser`'s built-in invite is the only mechanism that ever knows the temporary password; routing it through `Notifier.send` would mean generating that secret ourselves and putting it in a plain-text SES relay this codebase does not otherwise treat as credential-safe, in place of Cognito's own security-reviewed delivery path (the same one `SignUp`'s email-OTP flow already trusts). **The deactivation notice does go through the Notifier** (`clinicianDeactivated`, `packages/i18n/src/notifications/index.ts`) — no credential involved, and best-effort: a failed send is logged and does not undo or fail the deactivation, which is already real and already audited by that point.
- **`services/api/src/dynamo-notification-log.ts`** (new) — `DynamoDeliveryLog`, `DeliveryLog`'s first durable implementation. Built now, not deferred, because this task is the **first production caller** of `Notifier.send` (2.3.1 built the abstraction with nothing calling it yet) — "the gate that precedes its first real use," the same phrase `09-self-audit.md` uses throughout this plan for every other deferred piece. Append-only by the same three mechanisms `dynamo-audit-log.ts` uses; no read side, because nothing has asked for one yet.
- **`infra/src/data-stack.ts`** — `ClinicianAdminFunction`, scoped to: `dynamodb:GetItem`/`PutItem` on `CLI#*`; `dynamodb:PutItem` on `AUDIT#*` and `NOTIFICATION#*` (write-only on both — this role never queries either back); `cognito-idp:AdminCreateUser`/`AdminDisableUser`/`AdminEnableUser`/`AdminUserGlobalSignOut`/`AdminGetUser` on the clinician pool ARN and nothing wider; `ses:SendEmail` on the existing verified identity. `attachDestructiveActionGuardrail` and `attachAuditPartitionReadGuardrail` apply, same as every other role.
- **`packages/eslint-plugin-no-destructive`** — `AdminDeleteUserCommand` joins `BANNED_IDENTIFIERS` (the same set `DeleteItemCommand`/`DeleteObjectCommand`/`DeleteRequest` already sit in). This is the task's "no code path calls `AdminDeleteUser` — a repo-wide assertion in the same family as `lint:no-destructive`" line, implemented as an extension of that exact mechanism rather than a bespoke test: the ban is repo-wide (every package, not just `services/api`), enforced at lint time (every `pnpm -r lint`, already required CI), and — per the rule's own no-disable-comment guard (`docs/runbooks/destructive-primitive-lint-rule.md`) — cannot be silenced with an `eslint-disable` comment either.

## Verification

- `clinician-repository.test.ts` — a second principal is rejected (`PRINCIPAL_ALREADY_EXISTS`); any number of subs alongside the one principal; a deactivated record's row stays fully readable, name and role intact; `role` never changes through deactivate/reactivate; one audit row per creation and per transition, with the acting principal.
- `dynamo-store.test.ts`'s new `DynamoClinicianStore` cases — the atomic marker write for a principal, none for a sub; the `TransactionCanceledException` → `RECORD_ALREADY_EXISTS`/`PRINCIPAL_ALREADY_EXISTS` disambiguation via the follow-up `get()`.
- `clinician-admin.test.ts` — create calls Cognito before the repository, in that order; 403 for a sub-clinician and for a patient; 401 with no verified principal; 404 when the flag is off; 400 on an invalid body (and Cognito is never called); 409 on a second principal; deactivate performs all three of record/disable/revoke and sends the notice; the notice failing to send still returns 200; 404 for an unknown id; reactivate enables the Cognito user.
- `dynamo-notification-log.test.ts` — the delivery log writes exactly the record's own fields, never a spread; a key collision throws rather than overwrites.
- `no-destructive-primitives.test.js` — `AdminDeleteUserCommand` is now a banned identifier; `AdminDisableUserCommand`/`AdminEnableUserCommand` are unaffected (valid cases).
- `infra/src/data-stack.test.ts` — updated counts (11 audit-table-holding functions, 11 audit-partition/keyless-read denials, 10 flag-reading functions) and two tests rewritten to their now-true state: the API Gateway authorizer resource exists (count 1, not 0) and exactly this task's three routes are behind it — both tests' own prior comments said "when this assertion starts failing, that is the task landing, not a regression," and this is that task. The registration function's own cognito-idp-permission test is narrowed to that function's own policy (it used to scan the whole template, which is no longer a valid check now that the clinician-admin function legitimately holds `cognito-idp:Admin*` grants).

**Not independently tested, and why that's sound:** "a deactivated clinician's token is refused within the authorizer's cache window." This is `authorizer.ts`'s existing, already-tested behaviour (`OPERATIVE_STATUSES` excludes `deactivated`) acting on a fact this task is responsible for making true — that `account_status` really does flip to `'deactivated'` on the row the authorizer reads. That flip is what `clinician-repository.test.ts` proves; the authorizer's reaction to it is TASK 2.2.2's own proven property, not new surface this task introduces.

`pnpm -r lint && pnpm -r typecheck && pnpm -r test` — all green.

## What was deliberately not built here

- **Role transfer.** See above — not required by this task's own Tests/DoD, and no consumer needs it with exactly one principal in existence.
- **Provisioning a real clinician (the principal, "You").** This task builds the mechanism; using it — inviting the first real clinician account — is an operator action once the flag is turned on, the same as every other default-off flag in this plan.
- **A read side for the delivery log**, matching `notification-log.ts`'s own precedent — no task has asked for one.

£0.00 net-new — one more 128 MB arm64 function inside the always-free Lambda allowance, and its writes (a handful of clinician accounts, ever) are immaterial against `03-cost-model.md`'s existing DynamoDB and SES lines.
