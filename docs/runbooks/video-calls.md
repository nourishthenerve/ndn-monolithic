# The peer connection, its ICE-failure fallback, TURN, and the relay cap (TASK 4.3.1, TASK 4.3.3, TASK 4.4.1, TASK 4.4.2)

**Date:** 2026-08-27 · **Tasks:** [05-execution-plan.md § TASK 4.3.1](../plan/05-execution-plan.md), § TASK 4.3.3, § TASK 4.4.1, § TASK 4.4.2 · **Requirements:** D-12, R-03, FR-VID-04 · **Depends on:** 4.2.2 (TASK 4.3.1); 4.3.1 (TASK 4.3.3); 4.2.1, 4.3.3 (TASK 4.4.1); 4.4.1 (TASK 4.4.2)

## What this covers

Every prior Phase 4 task moved signalling messages between two joined sockets; nothing did anything with them. **TASK 4.3.1** is where `RTCPeerConnection` first appears in the codebase, on both sides of the account shell: a signed-in patient or clinician who reaches the call page, for a scheduled appointment they are a party to, gets a real STUN-only WebRTC call with the other party. **TASK 4.3.3** is what a call does when that STUN-only ICE fails: one automatic retry, then a legible terminal state, never TURN. **TASK 4.4.1** is the retry's own second tier — a short-lived, per-call Cloudflare TURN credential, requested only once STUN alone has already failed. **TASK 4.4.2** is R-03's own remaining mitigation: a concurrent-relay cap that doubles as the kill switch, and an early-warning CloudWatch alarm on estimated TURN spend.

## What was built

- **`apps/web/src/account/webrtc-signalling-client.ts`** — the SDK-free half of this task's own split, mirroring `services/api/src/ws-join.ts`/`ws-relay.ts`'s "business logic in one file, wiring in another" shape. `parseIncomingMessage` (Zod) rejects anything not matching one of `joined` / `join-denied` / `peer-unavailable` / the `offer`/`answer`/`ice-candidate`/`leave` relay envelope, returning `undefined` rather than throwing — the identical "not a recognised shape, dropped, never a crash" posture `ws-default-handler.ts` already takes for a message travelling the other way. `connectSignalling` opens the `WebSocket` with `?token=` (TASK 4.1.1's own constraint: a browser `WebSocket` cannot set an `Authorization` header on the handshake) and sends `{ type: 'join', appointmentId }` the moment the socket opens, not before.
- **`apps/web/src/account/VideoCall.tsx`** — one component, shared by both sides of the account shell. Constructs `RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.cloudflare.com:3478' }] })` once `DeviceCheck.tsx` (TASK 4.3.2) hands off a device stream and the WebSocket has `joined`, attaches its tracks, and wires `ontrack` to a remote `<video>`. Offer/answer roles are fixed, not raced (this task's own step 2): the patient always offers, the clinician always answers. ICE candidates trickle over the same relay as they arrive, buffered if they arrive before this side's own `setRemoteDescription` resolves.
- **`apps/web/src/account/call-state-machine.ts`** (TASK 4.3.3) — where `CallConnectionState`/`CallLifecycleState` now live (moved out of `VideoCall.tsx` to avoid a circular import once this file existed). `VideoCall.tsx` feeds it every `RTCPeerConnection.connectionState` transition; it decides `connecting`/`connected`/`reconnecting`/`call-failed` and calls `onRetry` at most once per failure. `VideoCall.tsx`'s own `onLifecycleChange` prop is TASK 4.5.1's seam onto this type.
- **`apps/web/src/pages/[locale]/account/call.astro`** — the account-shell page. Statically generated and empty, same discipline every other authenticated account page in this codebase already states.
- **`packages/i18n/src/locales/en.json`** — the `videoCall.*`/`deviceCheck.*` catalogue entries this page and its components need (loading/forbidden/error/waiting/reconnecting/connection-state/join-denied-reason/device-permission copy).
- **`apps/web/src/site-config.ts`** — `signallingWebSocketUrl`, the real deployed `wss://93im3xehxh.execute-api.eu-west-2.amazonaws.com/$default` (`NdnDataStack`'s `SignallingWebSocketUrl` output), hardcoded the same way `contentApiUrl` already is and for the identical reason stated there.

## Two real constraints this task surfaced

**Not `[appointmentId].astro`, on purpose.** The plan named this file with a dynamic path segment; the actual infra cannot serve one. ADR-0017's static build writes a fixed set of files to `dist/`, and `web-stack.ts`'s CloudFront distribution has no SPA-style fallback — a missing S3 object 403/404s straight to `404.html`. `[slug].astro` works for `blog`/`workshops` only because their own `getStaticPaths` enumerates every id that exists *at build time* (published content); an appointment id has no such enumeration, and nothing in this codebase queries DynamoDB from `astro build` for anything patient-identifying regardless. The actual, working route is one static page, `call.astro`, and the appointment id travels as `?appointmentId=`, read once client-side by `VideoCall.tsx` — the same "resolve everything at runtime, bake in nothing" posture `messages.astro`'s own `/patients/me/messages` `me` resolution already established for a different unknown. This is a gap named here rather than discovered mid-implementation, the same posture TASK 4.1.1's own header comment takes for the WebSocket auth-header constraint. TASK 4.5.1's join button is what will link here with the real query string.

**Where `role` comes from.** The fixed offer/answer roles mean this component has to know, before it does anything else, whether the signed-in caller is the appointment's patient or its clinician — and nothing hands it that directly. The WebSocket `joined` response carries no role (`ws-join.ts`), and `session.ts`'s own header states `SessionClient` deliberately never decodes the access token's claims. `VideoCall.tsx` resolves this the same way `PatientProfile.tsx`/`CaseloadView.tsx` already treat a `403` as an ordinary, expected outcome: it calls the existing `GET /clinicians/me/calendar` (`appointment.ts`, reachable by either clinician column on the `Appointments` matrix row, refused for a patient by construction) and reads `response.ok` as the role signal — `200` means clinician, anything else means patient. A wrong guess here is harmless: the real boundary stays server-side, in 4.2.1's own `can()`/window/status checks on the actual join.

**The `video.call.enabled` flag named in the plan's own Flag line has no code-level gate in this task.** This task's own Files list touches nothing under `services/api` or `flags.ts`, and no frontend flag-reading mechanism exists in this codebase yet (every prior flag is read server-side only). The page is reachable once built and deployed, but functionally inert unless `video.signalling.enabled` (WS `$connect`) and `video.callAuthz.enabled` (the join decision) are both on — the identical "off means functionally inert, not code-absent" shape TASK 2.2.4's `auth.webSignIn.enabled` already establishes for the account pages generally. A guessed or shared URL with a real `appointmentId` still cannot get past `join-denied: not-available` if `video.callAuthz.enabled` is off, and cannot even open the socket if `video.signalling.enabled` is off.

## What was built, continued: the `peer-unavailable` retry

A patient who joins moments before their clinician is the ordinary case, not a failure — 4.2.2's `ws-relay.ts` returns `peer-unavailable` to the sender whenever the other party has not joined yet, and nothing about the join window guarantees simultaneity. Only the offerer (the patient) ever sends a message that can bounce this way — the answerer sends nothing until it has received an offer. `VideoCall.tsx` retries the *offer* alone (never the join) every 2 seconds, up to 15 attempts (~30 seconds), surfacing a `waiting-for-peer` status meanwhile; exhausting the retries reaches the same `call-failed` state TASK 4.3.3's own state machine owns. This is narrowly the "other party hasn't joined yet" case, distinct from what TASK 4.3.3 owns below (an ICE failure *after* a connection was actually attempted).

Trickle ICE candidates arriving before this side's own `setRemoteDescription` resolves (a well-known WebRTC race, more likely here given the relay's own network hop) are buffered and flushed once the remote description is set, rather than thrown past the caller.

## What TASK 4.3.3 added: the ICE-failure fallback

- **`apps/web/src/account/call-state-machine.ts`** — `createCallStateMachine`, a small, SDK-free reducer. `failed` (or `disconnected` held past a named 3-second grace period, so a momentary blip is never mistaken for a real failure) transitions to `reconnecting` and calls `onRetry` exactly once; a second failure reaches the terminal `call-failed`; `connected` resets the one-retry budget, so a later failure in the same call gets its own fresh attempt rather than going straight to terminal.
- **`VideoCall.tsx`**'s `retryConnection` (the `onRetry` implementation) closes the failed `RTCPeerConnection` and builds a fresh one over the same already-joined call — the relay and the `CALL#` row are untouched, only the peer connection is rebuilt, per this task's own step 2.
- `call-failed` renders as a real `role="alert"`, never a blank screen. A signalling-socket close is kept as its own separate `'ended'` stage, not folded into this state machine — a peer connection can still be happily `connected` over an already-negotiated P2P path with no further use for the socket.

## What TASK 4.4.1 added: TURN

- **`services/api/src/turn-credentials.ts`** (new) — `POST /calls/{appointmentId}/turn-credentials`. Gated by `can()`'s own `'join-call'` decision (TASK 4.2.1, called rather than re-implemented) plus one check `can()` cannot express: the caller must hold a live, unexpired `CALL#<appointmentId>` row (`connection-repository.ts`'s `CallParticipant` gained a `ttl` field for exactly this — data it already stored, only now exposed on the type). Neither check re-derives the appointment's own status/window — a live `CALL#` row could only exist because `ws-join.ts`'s own checks already passed at join time. On success, calls Cloudflare's real TURN credential-generation API (`rtc.live.cloudflare.com/v1/turn/keys/{keyId}/credentials/generate`) and returns a 5-minute, per-attempt `iceServer`; the credential itself is never logged.
- **`services/api/src/turn-credentials-handler.ts`** (new) — the AWS wiring: real `AppointmentRepository`/`DynamoConnectionRepository`, and the Cloudflare API token resolved once per cold start from SSM (`getApiToken`, mirroring `contact-form-handler.ts`'s own `getTurnstileSecret`).
- **`infra/src/config.ts`** — `CLOUDFLARE_TURN_KEY_ID` (left empty, a manual Cloudflare dashboard step, the same "not something CDK can provision" category `TURNSTILE_SECRET_PARAMETER_NAME`/`SMS_ORIGINATION_IDENTITY` already document) and `CLOUDFLARE_TURN_API_TOKEN_PARAMETER_NAME` (`/ndn/cloudflare-turn-api-token`, an SSM SecureString populated the same out-of-band way). **[Owner action]** create a Cloudflare Realtime/Calls TURN key and run `aws ssm put-parameter --name /ndn/cloudflare-turn-api-token --type SecureString --value <token>` before `video.turn.enabled` can do anything real — until then, every credential request 502s and every retry simply falls back to STUN-only, never a hang.
- **`infra/src/data-stack.ts`** — a new `TurnCredentialsFunction`/route (`ContentHttpApi`, not the WebSocket API — a caller already knows its own `appointmentId` and gains nothing from the signalling socket for one request/response), reading `PAT#*` (the appointment) and querying `CALL#*` (the live-join check), plus `ssm:GetParameter` scoped to the one Cloudflare token parameter.
- **`services/api/src/flags.ts`** — `video.turn.enabled`, default off, independent of the two Phase 4 flags before it — a call that works P2P and simply fails without a relay option is a safe, cheaper intermediate state to prove before spending anything against Cloudflare's free tier.
- **`apps/web/src/account/VideoCall.tsx`**'s `retryConnection` now asks for a TURN credential before rebuilding the peer connection, and adds it to `iceServers` for that one attempt only (`fetchTurnIceServer`, never throws — a denial, flag-off, or provider failure are all the same "no TURN entry this time" outcome, and the retry proceeds STUN-only exactly as TASK 4.3.3 already built). `call-state-machine.ts` itself needed no logic change — its `onRetry: () => void` contract already covered a caller doing async work inside it.

## What TASK 4.4.2 added: the concurrent-relay cap and egress telemetry

R-03's mitigation list is three items — "concurrent-relay cap; egress telemetry + alarm; kill switch degrades to audio-only" — built here as one mechanism, not three: the cap, enforced at credential-issuance time, *is* the kill switch, because TASK 4.3.3's fallback already treats "no TURN available" as a legitimate path to its own terminal or STUN-only-continues state, not a crash.

**The cap is per call, not global.** `services/api/src/turn-credentials.ts`'s own `findCallParticipants` read (already fetched for the live-join check) is scoped to one `CALL#<appointmentId>` partition — at most two rows, ever — so a system-wide concurrency counter cannot be built from it without a new GSI this task's own Files list does not include. Read literally, Step 1's "count of unexpired `CALL#` rows … filtered to a `turnActive` flag" already describes exactly this per-call count: `MAX_CONCURRENT_TURN_RELAYS_PER_CALL = 1` refuses a second party's credential once the *other* party in the same call already holds one — the real, enforceable protection against the worst case R-03 actually names (relaying *both* directions of one call, doubling that call's own contribution to the modelled 1,000 GB/month ceiling), not a global cap the existing infrastructure has no cheap way to compute. A caller's own prior `turnActive` row never counts against their own later request — only the other party's does.

- **`services/api/src/connection-repository.ts`** — `CallParticipant` gains `turnActive?: boolean`; `markTurnActive(appointmentId, connectionId)` sets it via a conditioned `UpdateItem` (`attribute_exists(pk)`, so it can never create a row) — never cleared, the conservative direction to err in, the same "no destructive primitives" discipline this row's own TTL reclaim already relies on for cleanup.
- **`services/api/src/turn-credentials.ts`** — refuses with `{ error: 'FORBIDDEN', reason: 'relay-capped' }` once the cap is reached; marks the caller's own row `turnActive` immediately after a successful issuance.
- **`services/api/src/ws-relay.ts`** — `type: 'leave'` gains an optional `turnDurationSeconds`; `ASSUMED_TURN_RELAY_BITRATE_MBPS = 1.5` (an honestly-stated estimate — Cloudflare's real per-call usage figure is not visible from inside AWS) converts it to an estimated GB, attached to the relay decision regardless of `forward`/`peer-unavailable` (the estimate is about the sender's own usage, not the recipient).
- **`services/api/src/ws-relay-handler.ts`** — emits the `Ndn/Video` / `EstimatedTurnRelayGB` CloudWatch custom metric; a `PutMetricData` failure never fails the relay itself.
- **`apps/web/src/account/VideoCall.tsx`** — accumulates connected-while-TURN-assisted seconds across every retry in one call, and sends `{ type: 'leave', payload: { turnDurationSeconds } }` once, on unmount, only if that total is greater than zero — a call that never touched TURN reports nothing, never a fabricated zero.
- **`infra/src/config.ts`** — `TURN_RELAY_METRIC_NAMESPACE`/`TURN_RELAY_METRIC_NAME` (mirrored as literals in `ws-relay-handler.ts`, the same services-api/infra split `TURNSTILE_SECRET_PARAMETER_NAME` already documents) and `TURN_RELAY_ALARM_THRESHOLD_GB_PER_DAY = 17` — half the free tier (500 GB), expressed as a daily rate (500 ÷ 30 ≈ 16.7) so a one-day CloudWatch alarm period, this stack's own existing convention, can watch it.
- **`infra/src/budget-stack.ts`** — `TurnRelayVolumeAlarm`, notifying the same SNS topic `LogIngestionVolumeAlarm` already uses, per this task's own instruction — an early-warning companion to the hard cap above, not a second enforcement mechanism.
- **`infra/src/data-stack.ts`** — `turnCredentialsRole` gains `dynamodb:UpdateItem` on `CALL#*` (the same statement as its existing `Query`, for `markTurnActive`); `wsDefaultRole` gains `cloudwatch:PutMetricData` (unscopeable — AWS's own constraint on that action, not a shortcut).

## Verification steps

Two real browser sessions, signed in as the matched patient and clinician for a real scheduled test appointment (`video.signalling.enabled`, `video.callAuthz.enabled` both on):

1. Both open `https://<host>/en/account/call?appointmentId=<patientId>%23<scheduledAt-iso>` inside the appointment's join window.
2. Each grants camera/microphone permission when prompted.
3. Within a few seconds (or up to ~30 if one side joined well before the other), both sides show `connected` and see/hear each other — on a network where P2P is reachable.
4. Joining outside the window, or as someone other than the appointment's own two parties, shows the same typed `join-denied` reasons TASK 4.2.1 already proves at the WebSocket layer, rendered here as plain-language copy instead of a raw reason string.
5. (`video.turn.enabled` on, a real Cloudflare TURN key provisioned) Blocking UDP on one side's own network forces a STUN failure; the call shows `reconnecting` once, then `connected` again via a Cloudflare-relayed session (visible in Cloudflare's own dashboard). With `video.turn.enabled` off, or no real key provisioned, the same forced failure instead reaches the accessible `call-failed` terminal state after its one retry — never a hang.
6. With one relay already active on a call (the previous step), forcing the *other* party's own STUN failure too gets `relay-capped` instead of a second credential — that side's retry stays STUN-only and, if the network genuinely requires TURN, reaches `call-failed` rather than relaying both directions at once.
7. Ending a TURN-assisted call: `aws cloudwatch get-metric-statistics --namespace Ndn/Video --metric-name EstimatedTurnRelayGB --statistics Sum --period 86400 --start-time <today> --end-time <tomorrow>` shows a non-zero datapoint; a call that never used TURN contributes nothing.

## What was deliberately not built here

- **No join button, and no reachable link to this page from anywhere else in the account shell.** TASK 4.5.1 owns the button, on both sides, that will link here with a real `appointmentId`.
- **No code-level gate for `video.call.enabled`.** This task's own Files never touch `flags.ts` for that specific flag, and the page's real behaviour rides entirely on the flags TASK 4.1.1/4.2.1/4.4.1 already built.
- **No global, cross-call concurrency counter.** TASK 4.4.2's own cap is deliberately per call (see above) — a system-wide counter would need a new GSI, which is a real, honestly-named gap rather than a mechanism this task's own Files list could build.

## Cost

£0.00 net-new for TASK 4.3.1/4.3.3 — Cloudflare's STUN service is free and unlimited, and the ICE-failure retry rebuilds a peer connection with no new AWS resource. TASK 4.4.1 is also £0.00 net-new in normal operation: within Cloudflare's re-verified 1,000 GB/month TURN free tier (`03-cost-model.md`, ≈85 GB modelled worst case), and every WebSocket/HTTP call either task makes is already inside TASK 4.1.1's own modelled message count or a single low-volume Lambda invocation per retry. TASK 4.4.2 adds ~£0.10/month — one more CloudWatch alarm inside D-18's own ~8-alarm budget (the 6th), plus one `PutMetricData` call per call that used TURN, both negligible at this account's traffic.
